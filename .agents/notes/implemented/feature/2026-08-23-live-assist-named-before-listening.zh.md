# Agent Note: Live-assist names the session before it listens

Status: implemented

[English](2026-08-23-live-assist-named-before-listening.md) | 中文

## Problem

开始面试助手会让识别器立刻上线，而此时会话本身对这次刚刚开启的运行什么也没显示。恰恰在面试者不再看屏幕、转而面对对方说话的那一刻，有两样东西是缺的。

会话是异步命名的，因此它先以默认名出现在列表里，过一会儿才被改名——通常是一两秒后，标题请求失败时则永远不会。连着跑好几轮的面试者看到的是一列同名会话，不逐个打开就分不清哪个是哪个。

背景资料在日志里、也在每个回答请求里，却不在屏幕上任何位置。这份资料在一个开始即关闭的对话框中编辑，并跨运行保存在浏览器存储中，因此某一次运行究竟用的是什么，从对话里无法核对：上一轮留下的过期简历会产出面向错误岗位的回答，而屏幕上没有任何东西能解释原因。

## Decision

开始一次运行按顺序做三件事，识别器排在最后。

开场事件 `live-assist/started` 由自己的 `ConversationNodeDefinition` 投影成一个 chat node，原样渲染全文，连换行一起保留。这次运行的每个回答请求携带的正是这段文字，因此这个节点是运行输入的忠实记录，而不是它的摘要——做截断就等于取消了展示它的意义。一次运行以开场事件自身的序号为标识，因此在一个会话里停止后再次开始会开出第二次运行，各自带自己的资料与节点。

随后标题请求先跑完，才轮到 `LiveAsrWorker.open`。于是会话从第一帧起就带着名字，「已经在记录、但列表里还是默认名」这个状态不复存在。

名字不值得让一次启动失败。没有 `sessionTitle` 服务、模型给不出标题、请求失败，这三种情况都保留默认名并继续打开识别器。被会话自身结束取消的命名不记为失败，与被取消的回答处理一致；命名途中被 dispose 追上的启动直接返回，根本不打开识别器。

## Alternatives considered

**保持 fire-and-forget 命名，只把背景资料加进会话。** 这是原本已发布的行为，不增加任何启动延迟。它输在：默认名窗口恰恰在这个功能被使用的场合最糟——连着安排几轮面试的人，正是那个没法在面试当中停下来手动改名的人；而且标题请求失败或卡在慢路由后面时，这个窗口是无界的。

**把资料写成 `user/message`，让普通聊天渲染器显示它。** 这样不需要自己的渲染器。之所以否决：`intervieweeNotes` 把 `user/message` 读作面试者为引导后续回答而输入的内容，于是资料会被二次喂进每一个回答请求；而且一条合成的用户消息在日志里与面试者真正发出的消息无法区分。

**把资料显示在面板里而不是会话里。** 面板按设计只有输入框旁的一行，而这份资料恰恰属于应当在刷新后留存、事后可回看的内容——这正是当初把转写与回答放进会话的那条理由。

**用第一句转写出的问题来命名会话。** 这样监听之前不需要任何请求，名字随第一句话到来。之所以否决：对方说的第一句话通常是寒暄；而且这会重新引入它本该消除的默认名窗口。

## Consequences

- 换来：会话从第一帧起就能在列表中辨认；对话里能看到这次运行用的是哪份资料。
- 代价：一次模型请求的启动延迟，由 `titleMaxOutputTokens` 限制。面板在这期间停在连接中，对方在这个窗口里说的话不会进入转写。
- 资料以明文出现在会话里，因此向对方共享整个屏幕时，它和面板一样会被看到。
- 背景资料为空时根本不会发出标题请求——`generateTitle` 提前返回——因此不带资料开始的运行不付这份启动延迟，也保留默认名。

## Testing

`tests/session.spec.ts` 直接断言顺序：假 worker 把自己的 open 记进与 rename 相同的数组，因此启动被钉成「先 rename 后 open」，而不只是「两件事最终都发生」。取消竞态由以下方式覆盖：把标题流卡住、在启动途中 dispose，然后断言没有发生改名、没有记录失败、识别器从未被打开。

`tests/background-definition.client.spec.ts` 覆盖这条投影，包括一个会话里的第二次运行获得自己的节点；`tests/panel.client.spec.tsx` 断言卡片渲染资料时不会折叠面试者输入的空白。
