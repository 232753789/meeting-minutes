# Agent Note: 会议纪要从失败的阶段续跑

Status: implemented

[English](2026-08-23-meeting-minutes-resume-at-the-failed-stage.md) | 中文

## Problem

重新解析一场会议会从保留的录音开始把整条链重跑一遍：转码、每一个 ASR 分片、每一次摘要请求。对真实发生的失败来说，这个代价是错的。

工作量严重后置。一场 90 分钟的会议是 18 个五分钟分片穿过一个 1.7B 模型，而长转写的总结是十几次串行 LLM 调用。真正终止一次运行的失败——一次远程 ASR 调用超时、总结路由短暂不可用、最终 JSON 无法解析、转写中途 Host 重启——都发生在大部分工作已经成功之后。重试把它们全部丢弃并重新付费；一个间歇性失败的路由可以让一个下午耗在反复的完整重跑上。

而且没有任何东西被保留下来以便做得更好。`completedChunks` 记录了 ASR 走到哪里，但分片文本本身存在一个内存数组里，随这次尝试一起消失，因此即使运行到最后一个分片才失败，也拿不出任何转写。

## Decision

处理过程是幂等的，重试只决定上一次尝试有多少内容留下来喂给它。

`process()` 从会议目录里现有的内容继续，无论这是第一次还是第五次尝试。已发布的全量转写会完全跳过格式转换与 ASR。否则 WAV 分片重新切分——它们是临时产物，相对推理开销极低——而上一次尝试已完成的分片从 `transcript-progress.json` 读回，不再送进模型。上一次尝试转码出的播放文件只要还在磁盘上就复用，因为 `normalizedAudio` 只在转码返回之后才写入。

`transcript-progress.json` 是新增的持久产物：`{ chunkSeconds, segments }`，每完成一个分片重写一次，在 `transcript.json` 发布后删除。它先于记录中的 `completedChunks` 写入，因此两次写入之间崩溃时，进度只会领先于记录，而不会丢掉下一次尝试本可以复用的转写文本。当它的 `chunkSeconds` 或长度与本次要转写的分片不再对齐时会被丢弃，这正是修改 `asrChunkSeconds` 仍然安全的原因。

摘要复用 `summary-requests.json`，该文件本来就为审计保存了每次请求及其输出。归并过程对同一份转写是确定性的，因此第 n 个请求会一模一样地重复，直到上一次尝试停下的位置：复用按位置进行，并在第一个系统指令或输入不同的位置结束。`readSummaryRequests` 只返回带输出的前导连续段——审计按发起顺序写入，因此第一个没有输出的位置就是上次停下的地方。生成最终 JSON 的那次请求从不复用：它的输出还要通过解析，而一个解析失败的已保存输出否则会在每次尝试中被重放。

`MeetingRetryMode` 是对应的 wire 词汇。`POST /meetings/<id>/retry` 默认续跑，`?mode=restart` 表示完整重跑，其他取值一律返回 400。完整重跑不是另一条代码路径——它删除进度与审计文件、清除派生元数据，之后同一个幂等的 `process()` 从头开始。

`resumeStage(record)` 是「提供什么」与「实际做什么」共用的唯一判断。状态投影把它作为 `resumeFrom` 发布（全量转写已发布时为 `summarizing`，录音已转码或已有任一分片完成时为 `transcribing`，否则不存在），`admitRetry` 查询同一个函数，因此浏览器显示的按钮与 Host 跳过的工作不可能不一致。它只对失败的会议给出答案：已完成的会议没有失败阶段，因此要求它续跑得到的是完整重跑。

有内容可保留时浏览器同时给出两个动作——**继续解析** 作为主操作，**重新解析** 在旁边——否则只给出完整重跑。

## Alternatives considered

**在两次尝试之间保留 WAV 分片。** 它们是续跑 ASR 唯一需要的输入，保留下来看起来是最直接的省法。因成本与脆弱性被否决：16 kHz 单声道 PCM 每小时约 115 MB，会为每一场曾经失败的会议长期占用目录；而崩溃留下的半写分片目录还需要自己的一套校验。重新切分只是一次确定性的 FFmpeg 执行，其开销相对它保护的推理可以忽略。

**把已完成的分片追加进 `transcript.json` 而不是单独的进度文件。** 这样能少一个文件。因为那样 `transcript.json` 的含义会取决于另外读取的一个元数据字段——它到底是「全量转写」还是「其中一部分」——而且该文件也没有位置存放对齐检查需要的 `chunkSeconds`。一个在发布时删除的独立产物，让「这个文件存在」和「转写尚未完成」成为同一句话。

**把已完成的分片存进 `metadata.json`。** 不新增文件，而且记录本来就每个分片重写一次。否决原因是那次重写会随转写增长：三小时的会议每个分片都要重写几百 KB，只为记录一个新分片。

**按内容而不是按位置匹配摘要请求。** 用系统指令与输入的哈希，就能在任意位置复用已完成的请求。作为没有收益的额外机制被否决：同一份转写的归并本来就产生同一串请求，按位置匹配得到同样的命中，而按内容匹配还要额外决定两个输入相同的位置该如何处理。

**用记录停下时的持久阶段来推断续跑点。** `stage: 'transcribing'` 意味着已有分片完成。否决原因是阶段说明的是这次尝试走到哪里，而不是磁盘上留下了什么——一条进度文件已丢失或不对齐的 `transcribing` 记录，会承诺一个它无法兑现的续跑。由产物来决定。

**把完整重跑设为默认、续跑设为显式选项。** 这样不带参数的调用方会保持原有行为。否决原因是它为最常见的问题默认了最贵的答案：重试一场失败的会议，通常就是为了越过失败的那一步。

## Consequences

- 得到：代价与真正失败的部分相称的重试。18 个分片转写完成后总结路由失败，现在只需重跑总结；转写中途 Host 重启，从它到达的那个分片继续。
- 代价：每个未完成的会议多一个持久文件；续跑的复用规则不会好过它的对齐检查——尺寸不符的 `transcript-progress.json` 会被丢弃而不是被信任。
- 续跑仍会重复一个工作单元：失败的那个分片或请求整体重做，最终 JSON 请求也总是重新发起。
- 转写发生变化的会议要重新支付全部摘要请求，因为每个输入都不同。这是正确结果，也是复用比较输入而不是只数位置的原因。
- 两次尝试之间可以修改 `asrChunkSeconds` 而不会污染转写：不对齐的进度被丢弃，会议从第一个分片开始转写。

## Testing

`tests/resume.spec.ts` 端到端驱动四条路径：ASR 从失败的分片继续（断言已完成的分片绝不会被第二次送进模型）、已发布的转写跳过格式转换与 ASR、完整重跑丢弃进度与审计文件，以及 Host 重启留在转写中途的记录。

`tests/summary.spec.ts` 让一次尝试在分段摘要中途失败，断言下一次尝试恰好重放已完成的那些、转写变化后不复用任何请求，以及解析失败的最终 JSON 会被重新请求而不是重放。

`tests/config-storage.spec.ts` 覆盖持久文件边界：可往返的进度，以及无法解析、不对齐、超长或不可读的进度与审计文件。

`tests/ffmpeg.spec.ts` 断言已转码的播放文件被复用、缺失时重新转码。`tests/http.spec.ts` 覆盖默认值、两种显式模式，以及其他取值被拒绝。
