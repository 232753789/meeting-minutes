# Agent Note：为 composer 的工具设一个抽屉

Status: implemented

[English](2026-08-23-composer-tool-drawer.md) | 中文

## 问题

两个插件把 `conversation.input.left` 当成挂功能的地方：会议纪要挂了一个光秃秃的麦克风图形，实时面试助手挂了一个写着「面试助手」的 ghost 按钮。两者读起来不像同一类东西；每多一个插件，这一行就多一个控件；而 composer 工具行占的正是文本框拿不到的宽度。再来第三个这样的插件，成为问题的就是这一行本身，而不是功能。

这个座位也没给用户任何可读的东西。单看一个图形，说不出录音之后音频会被怎么处理；一个文字按钮花掉一行宽度，也只说出了一个名字——决定一个人到底会不会点开它的那句话，两种呈现都放不下。

## 决定

新增列表 slot `conversation.input.tool`，承载用户去打开的功能；`conversation.input.left` 保持原义——自带交互外观、紧挨常驻 chrome 的小型控件。

每个条目在一个会话内**渲染两次**，由 `ComposerToolSeat.surface` 告诉这次渲染该画哪一面：

- `bar`——工具行里的图标、运行中工具的状态与控件，以及条目自己的对话框。
- `drawer`——可展开面板里的一行：图标、名称，以及一句说明它做什么的话。

`ComposerToolDrawer` 渲染这一行图标、箭头开关，以及它上方的面板，按账本中的每个 id 通过 `renderSlot(..., { only: id })` 各渲染一次。没有任何条目注册时整个抽屉不渲染任何内容，因此不装这些插件的部署不为它付出任何布局代价。

**open 标志由抽屉持有，而不是条目。** 一个条目的两次渲染不可能各自拥有一个对话框，而图标和抽屉行又必须打开同一个；于是该标志按条目 id 存放在抽屉里，以 `open` / `setOpen` 送达每一次渲染。从抽屉行打开时同时收起面板，否则面板正好挡住它刚打开的界面。同一时刻只有一个工具处于打开状态——这些对话框都是模态的。

**运行中的工具留在 `bar` 面上。** 抽屉关闭时会卸载它的行，因此用户需要盯着的状态——录音计时、识别器的聆听状态——不能放在那里。`bar` 是比面板存活更久的那一次渲染，也正好坐在用户本来就在看的那一行里。

抽屉不需要注册项携带图标或描述元数据，因为两面都由条目自己画。抽屉从账本里取的只是 id 列表，订阅方式与视图环相同。

共享的行外观是 `ui-primitives` 中的 `ChoiceRow`：图标、标题、可选的两行描述、可选的尾部状态。它放在那里而不是 `ui-conversation`，是因为 client bundle 纯度门禁把 `ui-primitives` 视为平台模块而放行，却拒绝从 `ui-conversation/client` 做跨插件值导入——也因为否则两个 meeting 插件会各自持有同样的十五行行标记。

## 考虑过的替代方案

**在注册项上放静态 `icon` / `description` 元数据，由抽屉画出全部呈现。** 这个版本里条目只渲染一次，全部呈现归抽屉所有。它需要在 `ui-slots` 里加一套 per-slot 的条目元数据机制（`KindOptions` 的 list 分支只有 `id` / `order` / `label`，没有可扩展位），需要一套 thunk 约定让文案跟随当前 locale，还需要给 owner 一条带类型的读取路径。被否决的理由是：改动更大而结果更小——`surface` 同样给了条目两面，却把每一条本地化字符串留在拥有它的插件里，还让运行中的工具画出抽屉本来无法描述的东西。

**条目只渲染一次，open 标志放在条目内部。** 两个插件此前的做法。一旦图标与抽屉行是两处 DOM，它就不成立：两次渲染各持有一个 `useState`，点抽屉行打开的对话框位于随面板一起卸载的子树里。

**把所有东西收进单一的「工具」入口。** 像素最省，但每个工具都多一次点击，而且藏起了正该由工具行展示的运行状态。图标行让已经开始的录音不必打开任何东西就看得见。

## 结果

- 得到：每多一个插件只多一个图标而不是一个带文字的控件，以及一个能用一句话说清自己做什么的位置。
- 代价：占这个座位的条目要写两个渲染分支。这是一次注册覆盖两面的价格，而抽屉分支就是一次 `ChoiceRow` 调用。
- `conversation.input.left` 目前没有随包发布的占用者。它继续保留声明：自带交互外观、紧挨访问模式与 plan chrome 的控件，与用户去打开的功能是两个不同的座位。
- 面板相对工具行定位，未使用 portal。它向上展开，因为这一行就在 composer 卡片的底部。

## 测试

`ui-conversation/tests/skeleton.client.spec.tsx` 用一份桩账本挂载 root：没有条目时不渲染任何 chrome；有条目时收起状态只渲染 `bar` 面，`drawer` 面仅在展开时出现；抽屉行的 `setOpen(true)` 收起面板，并把标志单独留在该条目的 `bar` 面上；第二个工具的座位会从第一个手里接过标志；面板外的 pointerdown 只收起面板，不影响已打开的工具。

`live-assist/tests/panel.client.spec.tsx` 与 `meeting-minutes/tests/browser-plugin.client.spec.tsx` 通过一个像抽屉那样持有标志的宿主驱动两个插件，断言抽屉面写出工具名称并加以描述，而正在聆听的识别器在那里报告自己的状态，不再提供重新打开设置的入口。
