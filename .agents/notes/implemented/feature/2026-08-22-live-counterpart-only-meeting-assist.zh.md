# Agent Note: Live counterpart-only meeting assist

Status: implemented

[English](2026-08-22-live-counterpart-only-meeting-assist.md) | 中文

## Problem

浏览器会议的参与者希望模型跟住对方在说什么并草拟回答，同时既不听见、也不回答参与者自己的发言。`dsh-meeting-minutes` 已经能录制会议，但它是一条批处理流水线：录制、转码、按 300 秒切块、转写、总结。它的产出在会议结束几分钟后才到；而实时提示除非在还需要作答时抵达，否则毫无价值。

有两个问题必须一并解决：把对方的音频与参与者的音频分开，以及缩短从对方提问到回答显示之间的路径。

## Decision

`packages/meeting/live-assist` 是一个独立的可选 Web bundle。`dsh-meeting-minutes` 未被改动；两者只共享磁盘上的模型目录。

### 隔离是物理的，不是统计的

插件对一个共享的浏览器标签页调用 `getDisplayMedia`，从不调用 `getUserMedia`。对方的声音由会议页面播放，因此落在被捕获的标签页音频里；参与者的声音从麦克风进入会议客户端的上行通道，从不到达标签页的输出。因此说话人分离没有必要——而且本来就是错误的工具，因为它是在已经混合了双方的音频上事后猜测谁在说话。

代价是覆盖面：只有 Chromium 系浏览器实现了标签页音频共享，而原生会议客户端不通过浏览器标签页播放任何声音，因此根本无法用这种方式捕获。

### 整句识别，因为这里用不上流式

Qwen3-ASR 支持流式推理，但仅限 vLLM 后端，而 vLLM 在 macOS 上无法运行。因此识别器用 silero-vad 切分，并通过 transformers 后端转写完整语句，音频以内存中的 `(ndarray, sample_rate)` 二元组传入——这是 `qwen-asr` 接受的形式，因此全程没有任何音频写入磁盘。

这把延迟下界固定在大约 2–2.5 秒：判定语句结束前的 `vadMinSilenceMs`（700 毫秒）、0.5–1.5 秒的识别，以及约 500 毫秒到首个回答 token。调低静音阈值是用打断换速度。如果 vLLM 将来在目标平台可用，流式识别会消掉第一项并缩短第二项。

### worker 里的两个线程

识别一个语句所需的时间与数秒语音相当，因此单线程 worker 会阻塞输入，在每次推理背后丢失音频。worker 在主线程读取 stdin 并做切分，在一个推理线程上运行模型，并用锁保护 stdout。会话按 id 多路复用：切分状态按会话隔离，推理串行，因为模型以 batch size 1 运行。

### 分诊是模型的工作，且并入回答请求

会议中的绝大部分内容都不是问题。这里没有采用单独的分类请求——那会给每个语句都加上一次完整往返——而是让回答请求本身以一行控制行开头：`SKIP` 或 `ANSWER`。`ControlLineSplitter` 从流中剥离该行，因此分诊不产生任何超出既有生成 token 的开销，而回答从其后的第一个 token 起就开始流式输出。不遵守该格式的模型被视为在作答，其文本被保留：丢弃一个可用的回答，比展示一个未经分诊的回答更糟。

### 每一句都作答，且按顺序

回答按听到问题的先后逐个生成，新语句绝不会取消正在生成的那一个。

早先的版本确实会取消，理由是「已经换了话题的对方使先前的回答失去价值」。实际使用暴露了这个判断的错误：识别器按静音切分，句中停顿会让一句话提前结束，其余部分片刻后作为第二句到达。取消丢弃的是真正问题的回答，只留下尾部残句；该残句随后在没有上下文的情况下被送进模型，被当成一个独立问题作答。问题真正堆叠时，排队的代价是延迟；而取消的代价是面试者正在等的那个回答本身。

被切开的语句不会被重新合并——每一句都按自身作答，这正是面试者所感知的「每个问题都有答案」。

### 问答存放在 dsh 会话中，而非面板里

启动识别器会新建一个会话并切换过去。每条转写和每个回答片段都作为 `live-assist/*` 事件追加其中，对话视图通过一个 `ConversationNodeDefinition` 把一条语句连同它的回答事件折叠成单个 chat node 来渲染。socket 只承载实时状态——语音边界、就绪、失败——因为只有这些没有理由比通话活得更久。

这推翻了先前「面试内容只存内存、不写任何东西」的决定。这次反转换来了可回看、可刷新的记录，代价是隐私：对方说过的一切都以明文留在磁盘上，直到该会话被删除。它同时继承了所有可选插件事件都适用的词汇表规则——未安装本 bundle 的构建会拒绝重建包含这些事件的会话，因为 `Session.append` 没有提供把事件标记为可忽略的途径。移除插件会使过去的面试会话变得不可读，而不只是不渲染。

一次监听运行的开场就是它的背景资料：`live-assist/started` 由自己的 `ConversationNodeDefinition` 投影成一个 chat node，原样显示全文。每个回答请求携带的正是这段文字，把它放在会话里意味着这次运行的输入可以从对话本身读到，而不必去翻日志。一个会话里停止后再次开始会开出第二次运行，各自带自己的资料与节点。

会话标题由同一条模型路由从背景资料生成，并在识别器打开之前完成保存，因此会话从第一帧起就带着名字，在列表中可辨认。启动为此多付一次模型请求，理由见[先命名再监听](2026-08-23-live-assist-named-before-listening.md)。名字不值得让一次启动失败，因此没有 `sessionTitle` 服务、模型给不出标题、请求失败这三种情况都保留默认名并继续打开识别器；被会话自身结束取消的命名不记警告，与被取消的回答一致。它使用 `SessionTitleService.rename`，该方法会以用户重命名的方式钉住标题并停止自动生成的调度——在这里是正确的，因为面试会话没有可供自动 provider 使用的用户提示词。

识别器运行期间，面板收缩为输入框旁的一行：状态点、当前状态、暂停、结束。session 作用域的 slot 会在会话变化时重新挂载，因此采集与 socket 的生命周期活在 React 之外的一个控制器里；启动是一次两步交接——旧会话的输入框记录请求，随后在新建会话中挂载的那个组件用该会话的 id 接手。

新建会话只发生在当前会话已有对话时。`workspaces.startSession()` 复用工作区已有的空白会话，因此在空白会话里请求切换会拿回同一个 id：没有重新挂载，交接便永远等不到接手方，面板停在「正在连接…」直到用户点结束，而识别器进程从未被启动。空白会话就地开始监听——它本就是「新建会话」会落到的那个会话，因此这既解开死锁，也不牺牲「面试内容不落进你原本的对话」这项保证。控制器据此区分两种启动：请求携带一个不得接手的会话时等待切换，不携带时由下一个 `adopt` 就地接手。

## Alternatives considered

**写入 `user/message` 与 `assistant/message` 而非自有事件类型。** 这样能免费获得现有聊天视图的渲染，并且在同一会话中对后续 agent 回合保持可见。之所以否决：`agent-loop` 是本仓库中 `assistant/message` 的唯一写入者，这类事件的含义是「模型经由 loop 作出了回复」，伪造它们会使插件的建议在日志、派生历史以及两个 SDK 中都与真正的 agent 回合无法区分。

**每个问题驱动一次真实 agent 回合。** 在各方面都是标准做法，回答也会是普通的 assistant 消息。之所以否决，理由是延迟与形态：loop 每次请求都会组装完整的系统提示词与工具目录，还可能调用工具，这意味着数秒延迟，以及一段为阅读而非为开口而写的回答。专用 preset 可以削减这些，但那道接缝仍然是为自主工作设计的，不是为两秒内给出提示设计的。

**扩展 `dsh-meeting-minutes`。** 它的生命周期是持久产物处理——存储、重试、重新处理、下载——而这些对一个不持久化任何东西的会话全都不适用。共用同一个包意味着让两套无关的生命周期挤在同一个设置界面之后。

**先抽出 ASR 能力接缝。** 干净的终局是一个 `dsh-asr` Service Definition，带本地与远程 provider，被两个包共同消费。这被刻意推迟了：批式分块转写与实时 VAD 切分识别尚未显现出共同的接口，而仅凭一个新消费者去发明一个接口，会把错误的契约固定下来。两个包之间重复的模型目录检查是已知代价，也是重新审视这件事的信号。

**云端流式 ASR provider。** 延迟更低、中文准确率更好，但它会把会议音频送出本机。本 bundle 选择了纯本地；远程 provider 属于上述接缝之后，而不是硬接在这个包上。

**采集双方并用说话人分离或回声消除区分。** 按上述决策部分所述予以否决：严格劣于采集路径本就免费提供的隔离。

**像 `dsh-meeting-minutes` 那样混合麦克风与系统音频。** 对会议纪要是正确的，因为每个人的声音都属于记录；在这里则会把参与者自己的话放进转写，并促使模型去回答它们。

## Consequences

- 换来：参与者的发言不可能进入转写，这由构造保证而非靠过滤；问答成为可回看、刷新后仍在的会话；回答在问题结束后约两秒开始出现。
- 代价：仅限 Chromium 系浏览器与基于浏览器的会议；延迟下界受整句识别约束；与 `dsh-meeting-minutes` 同时运行时会常驻第二份 Qwen 权重。
- Host 持有一个识别器进程，在没有会话超过 `workerIdleShutdownMs` 后释放，因此空闲机器不会一直占用加速器内存。
- `maxSessions` 限制并发面板数；socket 在超出后拒绝升级，而不是让每个会话都劣化。
- 串行回答意味着连续提问会让靠后的回答变慢。这是相对于「彻底丢失一个回答」而刻意做出的取舍。
- 对方说的一切都以明文写入 session 存储。音频从不写入：它在内存中解码并以数组形式交给模型。
- 回答流按 delta 逐条记录，与 `assistant/chunk` 一致，因此一场长面试的日志会以回答片段为主体。
- 背景资料以明文出现在会话里。向对方共享整个屏幕时，它和面板一样是可见的。

## Testing

TypeScript 部分在仓库的 `pnpm run test` lane 中以每文件 100% 覆盖率运行，其中包括用真实 `ws` 客户端连接真实 HTTP server 验证 socket 生命周期，以及用真实 Loader 组合验证插件注册与拆卸。

worker 的语句切分在 `packages/meeting/live-assist/python/test_segmenter.py` 中针对 `VADIterator` 的脚本化替身测试。这些测试发现了两个最关键的缺陷：`VADIterator` 已经对它报告的两个坐标应用了 `speech_pad_ms`，因此再补一次会把相邻语音拼接进来；以及最短语句下限必须扣除该补白，否则一段被补白到 550 毫秒的 150 毫秒咳嗽会通过 400 毫秒的下限。它们只需要 numpy，但 CI 的 Python lane 只覆盖 `python/sdk`，因此未被接入，必须直接运行：

```bash
python3 -m pytest packages/meeting/live-assist/python
```

这个缺口是刻意的，也是本包中主要的未覆盖风险：切分逻辑的回归不会被 CI 捕获。
