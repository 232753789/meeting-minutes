# Agent Note: Live-assist 用两个模型把同一个问题答两遍

Status: implemented

[English](2026-08-23-live-assist-second-detailed-answer.md) | 中文

## Problem

面试助手对每个问题只给一个回答，而一个回答无法同时满足面试者的两种需要。开口前三秒有用的是一句能照着念出口的结论和几条支撑它的要点；三十秒后有用的是另一样东西——对方追问「为什么」时，回答需要结论背后的技术机制、经历里的具体数字，以及这个方案在什么条件下不再成立。

调提示词到不了这两个目标。要求深度会让回答又晚又长，在有人等着你说话时根本来不及扫读；要求简短则恰好丢掉那些能扛住追问的材料。路由同样被过载了：同一个模型既要快到在面试者开口前就出现在屏幕上，又要强到能推理一道系统设计题——快的模型往往不强，强的模型往往不快。

## Decision

Host 可以再指定一条路由，每个被作答的问题都作答两遍。

`deepProvider` 与 `deepModel` 开启这条路，必须成对提供，并解析成一个可选的 `ResolvedConfig.deep`，因此「深度路是否存在」是一个字段是否存在，而不是四个字段是否彼此一致。`deepReasoningEffort`、`deepMaxOutputTokens`、`deepRequestTimeoutMs` 只约束这一个请求——推理路由需要比快速路长得多的截止时间和高得多的 token 上限，强行共用必然让其中一条错配。不填这一对时，插件仍然只发它一直在发的那一个请求。

**判定仍然只在快速路上做。** 第一个请求保留它的 `SKIP`／`ANSWER` 控制行，深度请求由这一行落在 `ANSWER` 上触发，而不是由这句发言本身触发。因此一句寒暄在深度路上不产生任何开销，两条路也不可能对「这句话是不是问题」给出互相矛盾的判断——那正是两边各自独立判定会带来的后果。深度提示词写明判定已经完成，要求它从第一个字符起就是内容。

**两条路各自排队。** 深度路由天生就慢，共用快速路的队列会让下一个问题的简短回答排在上一个问题的详细回答后面——而这正是快速路要避免的延迟。两条路各自持有自己的 promise 链；`settled()` 先排空快速路，因为向深度队列追加条目的正是它。

深度队列条目在入队时捕获历史与补充说明，而不是在执行时。慢速路由轮到某个条目时，会话可能已经回答了更晚的问题，而那些并不是这个问题被提出时所处的上下文。

两条路写同样的三个 answer 事件，用 `'fast' | 'deep'` 的 `track` 字段区分，而不是新增一套平行的 `deep-answer-*` 事件类型。投影把它们折叠进一个 `ExchangeChatData`，其中两个 `AnswerTrackState` 走同一条 `pending` → `streaming` → `done` 状态推进；卡片把它们上下堆叠：简短回答在上——它先到，且能在对方还没说完时读完——详细回答在它下方。只有两条路都在场时才显示标签，因为没有配置深度路的 Host 无从区分。未配置深度路的一次监听根本不会长出 `deep` 这条路，同一个渲染器覆盖两种部署。

深度回答不回灌为历史。`QaTurn` 保留快速回答：它短到可以携带八条，也已经写出了后续问题需要与之保持一致的那个结论。

## Alternatives considered

**两个请求同时发出，各自独立判定。** 这是对「两个回答同时提交」最字面的实现，且不需要任何协调。落选的原因是两个模型可能给出相反的判断：面试者会看到一句寒暄在一条路上被长篇作答、在另一条路上被标为无需作答，且无从判断该信哪一个。它还要为对方说的每一个语气词付出深度路由的 token。

**等快速回答生成完，再把它附在深度请求里发出。** 深度模型由此可以避开屏幕上已有的内容。落选的原因是这会让两条路首尾串行——详细回答要整整晚一个完整的快速回答才开始——而且快速回答是较弱模型的输出：把它喂进去会把较强的模型锚定在它上面，而不是让后者从问题本身重新推理。

**改成 N 条并行路由的 `answerRoutes` 数组。** 更通用，而且天然让两条路对称。落选的原因是没有任何场景需要第三个回答，UI 要为数量未知的流式区块做布局，而这里的两个角色本就不同——一个做判定，一个不做——用一组可互换的路由来表示会歪曲它们。

**新增独立的 `live-assist/deep-answer-*` 事件类型。** 好处是不必改动现有事件。落选的原因是两条路携带的信息完全相同，会导致同样的投影代码写两遍，而这正是仓库的对称性规则要拦住的不对称；一个判别字段就能保持单一代码路径。

**用标签页切换两个回答。** 两个回答都很长时屏幕更干净。落选的原因是详细回答到达时面试者正在读简短回答，而它恰恰是追问来临时要去看的东西：标签页把它的到达藏在一次点击之后，还要再加一个未读提示来抵消这个缺点。

## Consequences

- 得到：一个可以立刻说出口的回答，以及同一个问题上一个扛得住「为什么」的回答。面试者靠往下看来选择，而不是靠等待。
- 代价：配置深度路由后，每个被作答的问题的请求数大致翻倍、输出 token 不止翻倍，推理模型的思考过程还要另行计费。背景资料与历史要付两次费用。
- 详细回答在自己的一条路上排队，因此连续三个问题会让第三个详细回答姗姗来迟，尽管它的简短回答按时到达。
- 深度请求失败会上报到面板，同时快速回答照常成立；面试并不依赖深度路由可用。
- 未配置深度路由的部署里，卡片不会出现任何标签，原有的单回答体验逐像素保持不变。

## Testing

`tests/session.spec.ts` 覆盖两条队列所需的协调：被跳过的发言完全不产生深度请求、未配置时不产生深度请求、深度失败上报到面板而快速回答仍然完成，以及——通过一条被闸门卡住、跨两个问题占住队列的深度路由——正在飞行中的请求和排在它后面的条目都不会在会话结束后再写入回答。

`tests/answer.spec.ts` 钉住深度请求的路由、token 上限与 reasoning effort，并断言它的系统指令要求深度、且完全不提 `SKIP`。`tests/exchange-definition.client.spec.ts` 用两条路交错的事件折叠出状态，证明它们各自独立累积；`tests/panel.client.spec.tsx` 覆盖卡片的两种部署：有深度路时带标签堆叠，没有时不带标签。
